# BigWater Rail2: External Services

The third-party services the rail2 (sustainability quests) backend relies on. Compare
against the rail1 external-services document — the two platforms share very little
infrastructure (only Postgres, and indirectly Telegram/Privy conventions).

## At a glance

| Service                | Role                                                                               |
| ---------------------- | ---------------------------------------------------------------------------------- |
| GitHub                 | Source code hosting (`tosynthegeek/bigwater`)                                      |
| Railway                | Application hosting — API/worker process, bot process, Postgres, Redis             |
| Privy                  | Member and admin login                                                             |
| Telegram               | Secondary client: task list, proof submission, notifications, marketing broadcasts |
| AWS S3 (or compatible) | Proof-image storage                                                                |
| OpenRouter             | LLM call that scores a submitted photo's relevance to its task                     |
| Sightengine            | AI-image-generation detection on submitted photos                                  |
| Redis                  | BullMQ job queues, admin-login rate limiting, Telegram bot session storage         |

Note what's **absent** compared to rail1: no Stripe, no on-chain component, no
Netlify, no Discord/X integration, no Resend, no Twilio. Rail2 has no payments and no
NFTs — see the database document's scope note.

## Hosting and infrastructure

**GitHub** hosts the source, a single repository containing the API, the Telegram bot,
and the Drizzle migrations together (no separate frontend repos in this codebase —
the two staging frontend URLs referenced in the infrastructure document are deployed
from elsewhere).

**Railway** hosts everything else: the `api` service (HTTP API + in-process BullMQ
workers + schedulers, optionally the bot too), the `bot` service (standalone
long-polling Telegram bot), a managed Postgres instance, and a managed Redis instance.
See the infrastructure document for the full topology and deploy sequence.

## Identity

**Privy** is the front door for both regular members and admins. A member authenticates
with Privy client-side and sends the resulting access token as a bearer token; the
backend verifies it against Privy's JWKS and resolves (or lazily provisions) an
`auth_accounts` row keyed by the Privy DID. Admin login can also go through Privy
(the same token, checked against the same JWKS, but requiring the resolved account to
already carry the `admin`/`superadmin` role) — see the admin document for the full
login flow, including the separate password-based path that does not touch Privy at
all.

Privy is **not** the source of the wallet address rail2 displays for a member — that
comes from rail1's `users.wallet_address`, joined in via the shared `rail1_user_id`
link (see the database document).

## Cross-service link: rail1

Not a third-party service, but worth restating here because it behaves like one from
rail2's point of view: every first-time login for a regular member must present a
rail1-issued JWT (`X-Rail1-Token` header) that rail2 verifies **itself**, using a
shared secret (`RAIL1_JWT_SECRET`), rather than calling rail1's API. See the database
document, section 7, for the mechanics, and the infrastructure document for the
operational implication (the two services' secrets must be kept in sync).

## Community and engagement

**Telegram** is a full secondary client, not just a notification channel:

- A dedicated bot (token in `TELEGRAM_BOT_TOKEN`) runs long-polling via `grammy`.
- `/start <code>` links a Telegram account to a web-authenticated rail2 account, using
  a short-lived one-time code generated by the web app (`POST
/api/telegram/link-code`).
- `/tasks` lists available tasks as inline-keyboard buttons; tapping one starts a
  `grammy` conversation that asks for a single photo and submits it exactly like the
  web app's upload endpoint, tagged `source: "telegram"`.
- The bot also sends **push notifications**: submission-review outcomes (approved/
  rejected, with different copy for a member's first-ever submission or first-ever
  approval), and admin-triggered marketing broadcasts (`POST
/api/admin/telegram/broadcast`) to every member with a linked Telegram account.
- Session state for in-flight conversations (e.g. "waiting for a photo for task X") is
  stored in Redis via `@grammyjs/storage-redis`, so it survives a bot process restart.

There is no Discord or X (Twitter) integration in rail2 — those exist only in rail1's
quest system, which rail2 does not touch.

## AI-assisted review

Two independent third-party checks run against every submitted photo, in parallel,
inside a BullMQ worker running in the `api` process:

- **Sightengine** (`SIGHTENGINE_USER` / `SIGHTENGINE_SECRET`) — a single `genai` model
  check for whether the image looks AI-generated. Rail2 turns its `ai_generated`
  probability into a 0–100 "authenticity" score (`100 - probability%`).
- **OpenRouter** (`OPENROUTER_API_KEY`, model configurable via `OPENROUTER_MODEL`,
  default `qwen/qwen3.6-flash`) — a vision-capable LLM call that scores 0–100 how well
  the photo demonstrates the specific task's completion, plus a one-sentence rationale.

The two scores are combined (geometric mean, with a penalty cap if either score is
"drastically poor" — see the database document's evaluation section for the exact
formula) into the submission's `aiConfidence`/`aiVerdict` fields, and the submission
moves to `under_review` for a human admin to make the final call. Neither service ever
approves or rejects on its own.

There is also a code path for an **external** AI verification service to report a
verdict instead, via an API-key-authenticated internal endpoint
(`PATCH /internal/submissions/:id/review`, guarded by `AI_SERVICE_API_KEY`) — see the
API document's callout on this. As shipped, nothing calls that endpoint; the in-process
Sightengine/OpenRouter pipeline above is what actually runs.

## Storage

Proof photos and admin-broadcast images are stored via the AWS S3 SDK, pointed either
at real AWS S3 or, via `AWS_S3_ENDPOINT`, at any S3-compatible provider (MinIO,
Cloudflare R2, Supabase Storage, Backblaze B2). A CDN URL (`AWS_CLOUDFRONT_URL`) is
used to build the public links stored on each submission. See the infrastructure
document for the local-disk fallback driver used in staging/demo.

## Job queue and cache

**Redis** backs three unrelated concerns in this codebase, all through the same
`REDIS_URL`:

1. **BullMQ** — six queues/workers for submission evaluation, review notifications,
   new-task announcements, Telegram marketing broadcasts, and two recurring sweeps
   (monthly-tally banking, streak breaking). See the database document's "Queues and
   scheduled jobs" section for what each one does.
2. **Rate limiting** — a fixed-window counter for admin password-login attempts
   (`checkRateLimit` in `src/utils/time.ts`).
3. **Bot session storage** — `@grammyjs/storage-redis`, so a Telegram conversation
   (e.g. "waiting for the proof photo") survives a bot restart.
